# UT-003 — MarkItDownManager Component Test

## 구현 범위

`MarkItDownManager`의 의존성 주입 생성자에 테스트용 `FakeProcessRunner`와
`FakeExecutableResolver`를 전달하는 Qt Test component target을 추가했다. 테스트는
실제 MarkItDown executable, Python 환경, 외부 프로세스, 네트워크에 의존하지 않는다.

```text
MarkItDownManager
  ├── FakeProcessRunner
  └── FakeExecutableResolver
```

Fake runner는 started, stderr-ready, process-error, finished 신호와 stdout/stderr,
종료 상태를 테스트에서 동기적으로 제어한다. 임의 sleep이나 private member 접근 없이
`QSignalSpy`, 공개 `convert()` 및 `isRunning()` 계약만 검증한다.

## 검증 시나리오

- 정상 종료 시 UTF-8 Markdown 전달, 시작 인자와 UTF-8 process environment, running
  상태 전환
- 실행 중 두 번째 요청의 `AlreadyRunning` 및 중복 start 방지
- resolver가 빈 결과를 반환할 때 `ExecutableNotFound`; 설정 경로가 있으면 diagnostic에
  경로 포함
- process start 오류의 `FailedToStart`
- crash exit의 `Crashed`
- non-zero exit의 `NonZeroExit`, exit code와 멀티바이트 경계를 걸친 UTF-8 stderr 누적 및
  diagnostic decoding
- 성공 종료의 빈 stdout에 대한 `EmptyOutput`
- timed-out/write/read/unknown process 오류의 `ProcessFailure`
- `errorOccurred` 뒤 `finished`가 이어져도 실패 신호를 한 번만 전달
- 실패 뒤 새 변환에서 failure guard와 stderr diagnostic buffer 초기화
- 정상 및 모든 오류 종료 후 `isRunning() == false`

private helper인 stderr 수집, UTF-8 decoding, diagnostic 조합, 중복 실패 방지는 위 공개
신호의 error/details 값으로 간접 검증한다.

## Build integration

`tests/component/tst_MarkItDownManager.pro`를 추가하고 `tests/tests.pro`의 ordered subdirs에
등록했다. component target은 Manager와 실제 production adapter source를 링크하지만,
테스트 실행 중에는 Fake만 주입하므로 자식 프로세스를 시작하지 않는다.

## 검증 결과

2026-09-14에 Qt 6.11.0 / MSVC 2022 x64 Debug 환경에서 다음을 실제 실행했다.

1. `tests/tests.pro` qmake 성공
2. `nmake /NOLOGO debug`로 기존 네 Unit Test와 새 Component Test 빌드 성공
3. `nmake /NOLOGO check`로 등록된 다섯 test target 실행 성공
4. `tst_MarkItDownManager.exe` 직접 실행 결과 16 passed, 0 failed, 0 skipped
5. `MarkItDown_Desktop.pro` qmake 및 Debug 애플리케이션 빌드 성공
6. Debug 실행 파일 옆 `python-venv/Scripts/markitdown.exe --help` 성공

Component Test 자체는 모든 실행에서 Fake resolver/runner만 사용했으며 실제 MarkItDown
프로세스를 시작하지 않았다. 이번 작업에서는 GUI와 대표 문서의 실제 변환 흐름을
실행하지 않았으므로 검증 결과는 자동화된 Manager 계약과 빌드 회귀 범위이다.
