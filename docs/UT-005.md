# UT-005 — MainWindow UI Behavior Test

## 구현 범위

`MainWindow`의 Open → Convert → Editor → Preview → Save 흐름을 실제 `QAction`,
`QPlainTextEdit`, `QTextBrowser`, window title 및 status bar를 통해 검증하는 Qt Test UI
target을 추가했다. private helper는 직접 호출하거나 공개하지 않는다.

테스트는 다음 controlled dependency를 사용한다.

```text
MainWindow
  ├── DocumentController → FakeMarkItDownManager
  ├── ControlledMarkdownRenderer
  └── FakeMainWindowDialogs
```

`MainWindow`에는 위 dependency의 소유권을 전달받는 생성자를 추가했다. 기존 기본 생성자는
실제 `DocumentController`, `MarkdownDocumentRenderer`, native dialog 구현을 생성하므로
production의 파일 선택, 저장 위치 선택 및 메시지 박스 동작은 유지된다.
`IMainWindowDialogs`는 정적 `QFileDialog`/`QMessageBox` 호출을 대체하는 UI 경계이며,
`MarkdownDocumentRenderer::render()`는 controlled renderer가 요청 완료 순서를 정할 수
있도록 virtual slot으로 바뀌었다.

## 검증 시나리오

- Open action이 선택된 지원 문서를 현재 문서에 반영하고 자동 변환을 한 번 시작하는지 확인
- 변환 중 Open, Convert, Save, Save As가 비활성화되고 Convert 재요청이 전달되지 않는지 확인
- 변환 성공 후 editor 삽입과 최초 preview render가 모두 끝날 때까지 busy 상태를 유지하고,
  완료 후 editor/preview 및 control 상태를 갱신하는지 확인
- 변환 실패 후 Open/Convert를 복구하고 Save를 비활성 상태로 유지하며, 오류 title/message를
  dialog 경계에 전달하는지 확인
- editor 수정 후 debounce를 거쳐 최신 Markdown preview 요청을 만들고 결과를 적용하는지 확인
- A와 B render 요청에서 B가 먼저 끝나고 A가 늦게 도착해도 preview가 B를 유지하는지 확인
- Save action이 `QTemporaryDir`에서 선택한 경로를 `.md`로 정규화하고 Unicode Markdown을
  UTF-8로 저장하는지 확인
- 새 문서를 여는 동안 이전 문서의 pending render 결과가 도착해도 비워진 preview를
  오염시키지 않고, 새 변환 결과만 적용하는지 확인

비동기 검증에는 `QSignalSpy`, `QTRY_COMPARE_WITH_TIMEOUT`,
`QTRY_VERIFY_WITH_TIMEOUT` 및 event-loop barrier를 사용한다. `QThread::sleep`,
`QThread::msleep`, `QTest::qWait` 같은 고정 대기는 사용하지 않는다.

## 격리와 Build integration

`tests/ui/tst_MainWindow.pro`와 공통 `tests/ui/ui_test.pri`를 추가하고
`tests/tests.pro`의 ordered subdirs에 등록했다. source document와 저장 결과는 test마다
새 `QTemporaryDir` 아래에 만들며, 실제 MarkItDown executable, Python process, network,
native file dialog 또는 modal message box를 사용하지 않는다.

## 검증 결과

2026-09-14에 Qt 6.11.0 / MSVC 2022 x64 Debug 환경에서 다음을 실제 실행했다.

1. `tests/tests.pro` qmake 성공
2. `nmake /NOLOGO debug`로 기존 여섯 target과 새 `tst_MainWindow` target 빌드 성공
3. `nmake /NOLOGO check`로 등록된 일곱 test target 실행 성공
4. `tst_MainWindow.exe` 직접 실행 결과 10 passed, 0 failed, 0 skipped
5. `MarkItDown_Desktop.pro` qmake 및 Debug 애플리케이션 빌드 성공
6. Debug 실행 파일과 앱 로컬 `python-venv/Scripts/markitdown.exe` 존재 및
   `markitdown.exe --help` 종료 코드 0 확인

이번 작업에서는 실제 MarkItDown 문서 변환이나 interactive GUI smoke test를 수행하지
않았다. 따라서 검증 결과는 Fake/controlled dependency 기반 UI workflow, 기존 자동 회귀,
production 빌드 및 backend 설치 확인 범위다.
