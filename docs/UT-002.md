# UT-002 — MarkItDown Process Testability Refactoring

## 구현 범위

`MarkItDownManager`에 함께 있던 실제 프로세스 실행과 실행 파일 탐색을 다음 두 경계로
분리했다. 변환 결과 해석과 `ConversionError` 분류는 기존 공개 동작의 책임이므로
Manager에 유지했다.

```text
MarkItDownManager
  ├── IProcessRunner
  │       └── QProcessRunner ── production QProcess adapter
  └── IMarkItDownExecutableResolver
          └── MarkItDownExecutableResolver ── production discovery policy
```

기본 `MarkItDownManager(QObject *)` 생성자는 `QProcessRunner`와
`MarkItDownExecutableResolver`를 생성하므로 production 호출부인
`DocumentController`는 변경되지 않는다. 의존성 주입 생성자는 두 인터페이스의
`std::unique_ptr`를 받아 소유권을 명확히 이전한다. 테스트는 같은 생성자에 Fake를
주입하고 원래 Fake 포인터를 관찰용으로 유지할 수 있다.

## Process 실행 경계

`IProcessRunner`는 Manager가 실제로 사용하는 다음 기능만 노출한다.

- 실행 중 여부
- 자식 프로세스 환경 설정
- 프로그램과 인자 목록을 분리한 비동기 시작
- stdout/stderr 소비와 오류 문자열 조회
- started, stderr-ready, process-error, finished 신호

인터페이스의 exit status와 process error enum은 Manager가 `QProcess` 형식에 직접
의존하지 않게 한다. `QProcessRunner`가 Qt enum을 같은 의미의 인터페이스 enum으로
일대일 변환하고 실제 `QProcess` 신호를 전달한다. 범용 프로세스 프레임워크나
동기 대기 API는 추가하지 않았다.

## Executable Resolver

`MarkItDownExecutableResolver`로 옮긴 탐색 순서와 경로 판정은 기존 구현과 동일하다.

1. `MARKITDOWN_EXECUTABLE`에 지정된 파일 또는 PATH 명령
2. 애플리케이션 폴더의 `python-venv`
3. PATH의 `markitdown`
4. 애플리케이션/현재 폴더의 상위 경로에 있는 개발용 `python-venv` 또는
   `build/python-venv`

`IMarkItDownExecutableResolver::resolve()` 결과와 설정값을 Fake가 독립적으로 반환할
수 있으므로 개발 PC의 PATH, 앱 폴더 또는 Python 환경 없이도 Manager의
`ExecutableNotFound` 분기를 제어할 수 있다.

## 보존한 동작

- 프로세스 시작 전 `PYTHONUTF8=1`, `PYTHONIOENCODING=utf-8` 설정
- 공백을 포함한 입력 파일도 하나의 인자로 전달하는 `start(program, arguments)` 호출
- 실행 중 두 번째 요청의 `AlreadyRunning` 처리
- UTF-8 stdout 변환과 빈 출력 거부
- stderr 누적 및 오류 세부 정보 조합
- FailedToStart, Crashed, NonZeroExit, EmptyOutput, ProcessFailure 분류
- `errorOccurred`와 `finished`가 모두 도착할 때 실패 신호 중복 억제

## Build integration

다음 production 파일을 `MarkItDown_Desktop.pro`에 등록했다.

```text
src/markitdown/ProcessRunner.h/.cpp
src/markitdown/MarkItDownExecutableResolver.h/.cpp
```

이 티켓은 테스트 가능 경계와 주입 지점까지만 제공한다. Fake 구현과
`MarkItDownManager` lifecycle/error 컴포넌트 테스트는 의존 티켓 `UT-003`의 범위이므로
새 테스트 target은 추가하지 않았다.

## 검증 결과

2026-09-14에 Qt 6.11.0 / MSVC 2022 x64 Debug 환경에서 다음을 실제 실행했다.

1. `MarkItDown_Desktop.pro` qmake 성공
2. 새 Runner/Resolver와 변경된 Manager의 컴파일, moc, 링크 성공
3. Debug 애플리케이션 빌드 성공
4. 빌드 후 앱 로컬 `python-venv\Scripts\markitdown.exe` 준비 및 `--help` 실행 성공
5. `tests/tests.pro` qmake 및 기존 UT-001 네 target 빌드 성공
6. `nmake /NOLOGO check`와 네 테스트 실행 파일의 종료 코드 0 확인

이번 작업에서는 GUI 변환 흐름과 실제 문서 변환을 수동 실행하지 않았다. 따라서 위
결과는 production 빌드와 기존 deterministic Unit Test 회귀 검증 범위이며,
Fake 기반 Manager 시나리오 검증은 `UT-003`에서 수행한다.
